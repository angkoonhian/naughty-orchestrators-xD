The 8-step dispatch loop #

1. CLASSIFY single-repo / cross-repo / opinion / schema / UI / persona? 2. ASSESS IMPACT LOW / MEDIUM / HIGH / CRITICAL (with bump rule) 3. DA GATE da-lead + 7 universal critics + applicable platform-pack critics 4. ARCHITECT (if cross-repo) produces a change manifest 4.5 PRE-IMPL GATE 6 universal spec validators + platform-pack spec validators 5. ROUTE dispatch to Lead(s), parallel where independent 6. EXECUTE Leads + sub-specialists implement code 6.5 POST-IMPL GATE 5 code validators + qa-delegator wrapping project QA 7. SYNTHESIZE unify results, present to user with impact tier
Tier 0 (Claude Code itself) never writes code. It classifies, routes, synthesizes. Implementation always happens at Tier 1+.

Impact classification rules #

LOW skip all gates

  • Bug fixes without interface/schema change
  • Typo / copy / translation
  • CSS / styling-only
  • Config (.env, tsconfig, lint config)
  • Patch/minor dep bumps
  • Logs, comments, docs
  • Lint warning fixes

MEDIUM DA advisory, post-impl blocking

  • New features in single project
  • Refactoring
  • New dependency
  • New UI in existing app
  • New endpoints following existing patterns
  • Business-logic changes
  • Adding or modifying tests

HIGH all gates blocking

  • Cross-project changes (2+ projects)
  • DB schema changes
  • New API contracts
  • Auth / authz changes
  • Shared package changes
  • Removing / renaming endpoints
  • Deploy config changes
  • New data source

CRITICAL all gates + FOR/AGAINST debate

  • Architecture decisions
  • Technology migrations
  • New project creation
  • Auth model changes
  • New communication patterns (e.g., adding GraphQL)
  • Project merge / split
  • "Should we..." questions
Bump rule: changes touching security, authentication, or money → bump one tier higher.
Ambiguity rule: default to MEDIUM when unclear.

Tier-scaled gate behavior #

ImpactDA gatePre-impl gatePost-impl gate
LOW skipped skipped skipped
MEDIUM advisory (parallel, non-blocking) advisory blocking
HIGH blocking blocking blocking
CRITICAL blocking + structured FOR/AGAINST debate blocking blocking

Bypass conditions

  • User says "proceed anyway" → findings attached as warnings, gate passes
  • LOW impact → all gates skipped entirely
  • MEDIUM impact pre-impl → advisory only, no loop

da-lead router #

Located at docs/agents/cross-cutting/da-lead.md. Receives proposal + impact tier, reads .claude/orchestration.config.yaml, dispatches all applicable critics in parallel, collects findings, de-duplicates, synthesizes one verdict.

Verdict types

VerdictMeaning
PROCEEDNo CRITICAL or IMPORTANT findings; implementation can begin
PROCEED WITH CHANGESIMPORTANT findings; specific required changes listed
RECONSIDERCRITICAL findings; proposal needs rethinking

For CRITICAL impact, also produces a structured FOR/AGAINST debate block.

7 universal core DA critics #

All shipped with the skill. Installed unconditionally in every project at docs/agents/da/core/.

edge-case-critic
Null/empty/zero/million data points; timing races; session expiry mid-flow; browser quirks; off-by-one boundaries; partial-failure states.
security-critic
OWASP Top 10 against the stack: injection, broken auth, sensitive data exposure, XSS, CSRF, misconfiguration, broken access control.
performance-critic
Query plans at scale; N+1 patterns; bundle size; rendering perf; real-time fan-out cost; cache correctness; memory leaks.
failure-mode-critic
Queue down; cache unavailable; DB pool exhausted; third-party quota hit; network flake → duplicates; idempotency; graceful degradation.
consistency-critic
API shape consistency across consumers; event-naming; state-mgmt pattern alignment; cross-project parity; vocabulary drift.
tech-debt-critic
Pattern inconsistency; unnecessary deps; copy-paste; maintainability in 6 months; mixed paradigms; circular deps; ambient coupling.
alternatives-critic
Always produces output — forces Plan B. Names at least one simpler/different approach with explicit tradeoff. Never returns N/A or PASS.

Critic output format

[CRITICAL | IMPORTANT | MINOR] — <short title>
Concern: <what is the problem>
Why it matters: <impact if not addressed>
Mitigation: <specific fix or avoidance>
Evidence: <file:line or pattern reference>

End with PASS, ISSUES_FOUND, or N/A — no concerns in this domain.

Pre-implementation validators (6) #

Run after spec exists (post-brainstorming or post-architect), before any Lead is dispatched. Located at docs/agents/validators/pre-impl/.

problem-statement
Does spec clearly state the problem? Does it match user's actual request? Drift check.
requirement-completeness
Are all requirements stated and specific enough to implement? Any TBD gaps? Cross-system pieces specified?
success-criteria
Does spec define "done"? Are acceptance criteria explicit and verifiable? Could you write a test from this?
assumption
Are assumptions explicit and labeled? Risky/unverified assumptions that invalidate spec if wrong?
scope
Too big for one cycle? Too small? Multiple independent concerns bundled? Hidden scope creep?
contradiction
Internal contradictions? Section A vs B? Constraints vs goals? Architecture incompatible with requirements?

Gate decisions

FindingsResult
Any BLOCKERFAIL → loop back with smart routing
IMPORTANT only, no BLOCKERSCONDITIONAL PASS — findings carried forward, must address during impl
PASS or MINOR onlyProceed to ROUTE

Post-implementation validators (6) #

Run after Lead(s) finish implementation, before declaring done. 5 dedicated + qa-delegator (lives in cross-cutting) = 6 total.

spec-conformance
Per-requirement mapping: is every spec requirement implemented in the diff? Lists gaps.
acceptance-criteria
Each acceptance criterion verified against code. Per-criterion pass/fail.
diff-scope
Did implementer stay in scope? Rogue refactors / "while I was there" cleanups? Removed existing behavior?
regression
Existing tests still pass? Lists newly failing tests with output. Distinguishes from pre-existing failures.
smoke-test
Golden-path end-to-end check. HTTP request to new endpoint, page render, basic flow walkthrough.
qa-delegator (in cross-cutting/)
Wraps project QA (qa-lead agent or npm scripts). Classifies findings: security / performance / schema / test / type / lint.

Feedback loop machinery #

Failure-context payload schema

failure_context:
  gate: "pre-impl" | "post-impl"
  iteration: 1 | 2 | 3
  failing_validators:
    - name: "regression-validator"
      severity: BLOCKER | IMPORTANT | MINOR
      findings:
        - description: "Test X now fails"
          evidence:
            file: "src/__tests__/ticket.test.ts"
            line: 47
            output: "Expected 200, received 500"
          suggested_remediation: "Inspect TicketService.create()"
  prior_iterations:
    - iteration: 1
      what_was_tried: "<summary>"
      why_it_still_failed: "<reason>"
  routing_decision:
    target: "implementing Lead (support-lead)"
    reason: "Test failure is implementation-level"
Receiving agent's prompt always starts: "You are receiving this work back from validation. Address the listed findings and ONLY those findings."

Retry mechanics

PropertyValue
Counter scopePer user message, per gate
Hard cap3 retries per gate (max 6 per request)
ResetNew user message → both counters reset to 0
VisibilitySurfaces in response: "Pre-impl gate passed on iteration 2/3"
Cycle detection: compares failure signatures (validator name + finding hash) iteration-to-iteration. If iteration N+1 has the same primary blocker as N → abort early, escalate immediately. Prevents wasting all 3 attempts.

Migration protocol (7 phases) #

  1. Read existing state (root CLAUDE.md + docs/agents tree)
  2. Map existing → new universal slots
  3. Add new universal pieces
  4. Conflict resolution via AskUserQuestion — user chooses keep / replace / preserve-both
  5. Backup — everything copied to .claude/orchestration.backup-<YYYY-MM-DD-HHMMSS>/ before any modification
  6. Generate — write new files; existing only modified with user approval
  7. Report — summary of preserved, replaced, and added

Quick patterns #

"I want to use this skill on a fresh project"

cd /path/to/new-project
/orchestrate

Auto-detects fresh state, runs full pipeline (scan → infer → ask → generate).

"My project has an existing CLAUDE.md"

cd /path/to/existing-project
/orchestrate

Auto-detects Migrate mode. Backs up everything before any modification. Surfaces conflicts.

"I just added a new dep (e.g. stripe)"

npm install stripe
/orchestrate --update

Re-scans, shows added packs (stripe-payments would surface). Re-run /orchestrate to install.

  4. da-lead picks it up automatically

"Skill is too aggressive, gate keeps blocking"

Or: re-classify the request impact (use the bump rule rationale).
